Silent Failures at the Adaptation Seam: An Observational Audit of LLM Agent–Tool Ecosystems Across Four Domains, with a Registered Confirmatory ProtocolHuangyu RaoSchool of Geospatial Engineering and Science, Sun Yat-sen University, Zhuhai, ChinaAbstractLarge language model (LLM) agents act on external environments primarily through tool ecosystems originally designed for human operators and subsequently adapted for machine callers. When tools in such ecosystems fail, the most consequential errors are frequently silent: a tool call returns nominal success, the resulting output or committed state is incorrect, and the agent proceeds without flagging the discrepancy. This paper reports an observational audit—not a confirmatory experiment—of agent reliability across four domains (geospatial analysis, browser operation, tabular data processing, and desktop operation). Under a unified evaluation framework that distinguishes adapted legacy tooling, optional verification, mandatory verification, and agent-native packaging, we adopt the incidence of substantive-error consequences (rather than task completion alone) as the primary endpoint. In a browser-domain pilot (four models; 80 intention-to-treat design cells per model), post-adjudication substantive-error consequence rates ranged from 0.7750 to 0.9375, and a silently corrupted-value fault class penetrated every model and interface surface; adding an optional verification layer failed two of five pre-registered predictions (29/40 trajectories in substantive-error consequence). In a tabular-domain pilot (148 scored trajectories), outcomes split into 44 correct, 61 substantive-error consequences, and 43 incomplete trajectories with sharply model-dependent arm patterns; a failure-chain audit of one model–arm cell traced 22 of 24 substantive-error consequences to verification predicates that did not cover the injected fault and 2 to compliance fabrication against the gate. In the geospatial domain, case-level silent failures on live public services coexist with an explicitly unresolved governance state: formal evaluation ground truth remains unestablished (0/18 tasks), and the confirmatory governance gate remains closed. A desktop-domain stage-0 probe establishes only static-window snapshot stability for an accessibility-tree surface. Because pilot counts cannot support causal claims regarding verification design, our second contribution is a frozen, adversarially reviewed confirmatory protocol (C1) specifying a family-cluster randomised paired comparison of optional versus mandatory verification, exact sharp-null inference, and a composite availability gate; this protocol is registered as future work and has not been executed. Our bounded conclusion is that silent, consequential errors are pervasive at the human-to-agent adaptation seam, and that the field currently lacks confirmatory evidence identifying which interface mechanisms reliably reduce them.Keywords: LLM agents; tool use; silent failure; agent-native interfaces; fault injection; observational audit; pre-registration1. IntroductionLarge language model (LLM) agents do not act on the world directly; they operate through software tools. Most tool ecosystems currently available to agents share a common provenance: they expose interfaces originally built for human operators—desktop geographic information systems (GIS), web browsers controlled via automation APIs, data-processing libraries, and enterprise services—that were later adapted for machine callers, most recently through bridge or gateway layers implementing protocols such as the Model Context Protocol (MCP). Although this adaptation strategy is pragmatic and widespread, it fixes core interface properties—what an invocation signifies, what a return value certifies, what can be verified prior to execution, and what provenance accompanies an output—around design assumptions made for human users rather than autonomous callers.The failure mode of primary concern is not the explicit tool error. Explicit failures are comparatively well handled, as agents routinely recognise and recover from structured error signals. The far more hazardous failure is one that returns nominal success. We define a trajectory as a silent failure when a fault exists in the tool layer, the returned result or effected state is consequently wrong in a task-relevant manner, and the agent neither detects nor flags the discrepancy, instead propagating the erroneous output into subsequent actions or a final answer. A broader, consequential endpoint—measured as the primary outcome of this audit—is a substantive-error consequence: a delivered artefact, committed decision, or executed side effect that deviates from ground truth beyond a predefined task-level tolerance, irrespective of whether the agent detected an anomaly during execution.Two distinct research questions follow. Descriptively, how frequently do substantive-error consequences occur across current agent–tool ecosystems, under which fault classes do they arise, and where in the execution stack do they concentrate? Causally, does the wiring of verification within the interface—available for optional agent invocation versus enforced mandatorily on the execution path—alter error incidence, and does an ecosystem designed natively for agents behave differently from an adapted legacy interface over the same underlying data? While the causal question is scientifically central, pilot observations cannot answer it. This paper is structured around that epistemic asymmetry: it reports what an observational audit can rigorously support—incidence counts, fault distributions, mechanism-level case evidence, and limitations of the evaluation apparatus itself—and freezes, without executing, the confirmatory protocol required to identify causal effects.The audit spans four domains under a single framework. The geospatial domain serves as the programme's home domain, comprising an agent reliability laboratory evaluated against live public geospatial web services whose tool outputs were independently recomputed and adjudicated case by case. The browser domain provides the largest pilot, evaluating four models in a fixture-based web environment across a stock automation API, an agent-native surface, and an MCP sensitivity arm under clean and fault-injected conditions. The tabular domain pilots data-processing workflows evaluated against an independent deterministic script oracle. The desktop domain contributes a stage-0 feasibility probe of an accessibility-tree native surface. Across all four domains, we enforce a shared methodological discipline: frozen task sets and scoring rules, arm-blind scoring against an oracle independent of agent self-reports, explicit separation of infrastructure failures from model failures, and transparent reporting of every count alongside its intention-to-treat denominator.Three overarching findings organise the audit. First, substantive-error consequences are not rare edge cases: under injected faults they represent the modal outcome in our pilots, and one fault class—silently corrupted values embedded in well-formed responses—penetrated every model and interface surface in the browser pilot. Second, whole-package comparisons between adapted and agent-native surfaces yield small, model-dependent count differences in opposing directions; the audit offers no support for a blanket claim that native interfaces are inherently safer, and a pre-registered attempt to augment a native surface with an optional verification layer failed two of its five frozen predictions. Third, the binding constraints on agent reliability evaluation are increasingly epistemic rather than purely mechanical: in the geospatial domain, formal evaluation ground truth remains unestablished (0 of 18 tasks), the confirmatory governance gate remains closed, and one of the audit's most informative outputs is an explicit accounting of what cannot yet be claimed. Accordingly, we present the frozen confirmatory protocol (C1)—detailing its paired design, family-cluster randomisation, exact sharp-null inference, and composite availability gate—as a registered forward contribution, explicitly demarcated as unrun.The remainder of the paper is organised as follows. Section 2 situates the audit within existing literature. Section 3 defines the conceptual framework, experimental arms, primary endpoint, fault taxonomy, and three-tier evidence classification. Section 4 details the domain-specific audit protocols. Section 5 reports all pilot and audit counts by domain. Section 6 summarises the frozen confirmatory protocol (C1). Sections 7–9 discuss mechanism implications, structural limitations, and conclusions.2. Related WorkThis audit lies at the intersection of three literatures: agent interface design, fault injection and silent-failure analysis, and agent evaluation methodology. Below, we summarise the closest prior work; all citations are marked as placeholders pending verification, and no references are asserted in this draft.Interface design as an experimental variable. Controlled evaluations have demonstrated that modifying action formats, tool documentation, or interface granularity alone alters agent task performance under fault-free conditions [Wang et al., 2024; Hasan et al., 2026; Paschalides et al., 2026]. Whole-ecosystem comparisons have similarly contrasted agent-first APIs—featuring semantic verbs, dry-run previews, and evidence-bearing responses—against conventional CRUD APIs over identical underlying data models [Pan & Hou, 2026], while benchmark studies have held tasks, agents, and verifiers constant while varying only the software interface, including in desktop GIS environments [Wu et al., 2026]. Collectively, these studies establish that interface design affects task completion; however, they do not cross interface design with systematic fault injection, and they evaluate success rates rather than substantive-error consequences.Fault injection and silent failure. A parallel line of research injects faults while holding the tool ecosystem fixed, including matched-unit silent-error injection under frozen tool behaviour [Zhang et al., 2026], record-and-replay fault injection on MCP servers [Mazumder & Lia, 2026], and fault taxonomies mined from large corpora of real-world issue reports [Iannillo et al., 2026]. Perturbation studies of live vendor endpoints further indicate that failure honesty depends on constraint formalisation: machine-checkable constraints fail loudly, whereas prose-only constraints tend to fail silently [Li et al., 2026]. Audits of agent–tool chains in scientific computing ecosystems have likewise documented human-verified silent failures, frequently locating them at the wrapper layer adapting legacy APIs for agent consumption [Singh et al., 2026]. While this body of work confirms that silent failures are prevalent and measurable, it varies the model, agent harness, or fault mode rather than the tool ecosystem itself.Evaluation methodology. Methodological scholarship on benchmark validity—specifically denominator discipline [Hollis & Campbell, 1999], the distinction between case-series proportions and population rates [Dekkers et al., 2012], oracle independence [Sainz et al., 2023; Panickssery et al., 2024], and pre-registered adjudication rules [Nosek et al., 2018]—governs our reporting rules throughout. We adopt a deliberately conservative stance: pilot counts are reported strictly as descriptive counts, case series are treated solely as existence evidence, and causal language is reserved for the frozen confirmatory protocol in Section 6.The gap addressed by this research programme lies at the conjunction of these three streams: treating ecosystem nativeness and verification wiring as explicit experimental arms, applying an identical fault suite across arms, and pre-registering the substantive-error consequence rate as the primary endpoint. This paper delivers the observational half of that programme; the confirmatory half is frozen but unrun.3. Framework3.1 Experimental arms: adaptation, optional verification, mandatory verification, and native packagingAcross domains, comparisons are structured around four experimental arms defined over a shared underlying engine and data layer wherever feasible:Arm A (strong adapted baseline): Production software originally built for human operators, exposed to the agent via its standard programmatic API or a protocol bridge, accompanied by complete documentation, standard query and read-back capabilities, and reasonable retry logic. Arm A is intentionally configured as a strong baseline that retains all native safety controls of the underlying software.Arm B (optional verification): Arm A augmented with an explicitly callable verifier returning structured evidence and diagnostics, where invocation remains at the agent's discretion. The B–A contrast captures the aggregate effect of making verification available.Arm C (mandatory verification): Identical evidence sources and verification predicates to Arm B, but enforced as a mandatory gate on the execution path for guarded operations. The C–B contrast constitutes the programme's primary mechanism comparison, isolating the causal effect of mandatoriness while holding evidence and predicates constant.Arm D (native package): A tool ecosystem architected from the outset for agent callers—incorporating semantic contracts, session-scoped authorisation, true dry-run planning, evidence envelopes, and conformance testing—deployed as an integrated package. Because Arm D bundles multiple architectural changes simultaneously, A-versus-D comparisons operate at the deployment level and cannot isolate which individual component drives observed differences.Two analytical lines must remain strictly separated. The deployment line (Arm A versus Arm D) evaluates whole-package differences in practice; our browser and tabular pilots belong to this line, alongside an MCP sensitivity arm probing whether the baseline exposure mechanism (protocol bridge versus native API) alters observed outcomes. The mechanism line (Arm B versus Arm C) isolates the causal impact of verification wiring; it resides exclusively in the unrun confirmatory tier. Every quantitative finding in Section 5 is explicitly tagged with its analytical line.3.2 Primary endpoint: substantive-error consequence rateThe programme's sole confirmatory endpoint, established prior to any confirmatory data collection, is the substantive-error consequence rate: among all pre-allocated eligible trajectories, the proportion in which at least one predefined substantive error reaches a final deliverable artefact, a committed or implemented decision, or an unauthorised side effect. What qualifies as "substantive" is specified per task prior to execution via task semantics, set constraints, and numerical tolerances; trivial floating-point discrepancies are excluded. An error noticed by the agent still counts toward the endpoint if the erroneous consequence is ultimately committed; conversely, an erroneous candidate corrected within a staging environment prior to commitment is logged as a propagation-and-recovery event rather than a final error. Each trajectory contributes at most once to the primary numerator. Because refusals and timeouts constitute non-completions rather than automatic substantive errors, correct-completion rates and substantive-error consequence rates are always reported jointly; the primary endpoint is strictly distinct from $1 - \text{success}$.Trajectory outcomes across all domains follow a three-state taxonomy: S (correct delivery), H (substantive-error consequence; the harm state), and A (aborted or incomplete: no delivery, missing required components, or explicit abandonment). Pilot studies additionally log intermediate process indicators—evidence availability, evidence retrieval, anomaly recognition, corrective action, and final containment—strictly as descriptive diagnostics rather than causal estimates.3.3 Fault taxonomy and spatiotemporal specialisationInjected and naturally occurring faults are categorised by surface manifestation into five classes: F1 (explicit failure: timeout, raised exception, or structured refusal, used for calibration); F2 (silent value corruption: erroneous numbers, counts, or aggregates within syntactically valid returns); F3 (semantic misalignment: unit or coordinate-reference mismatch, silently dropped filter predicates, or entity confusion); F4 (stale or inconsistent state: superseded versions reused, read–write inconsistency, or concurrent overwrite); and F5 (permission and side-effect violation: scope misbinding, extraneous writes, or nominal success receipts inconsistent with committed state, restricted to tasks with explicit permission boundaries in isolated environments). Each scenario additionally records source layer, persistence, intensity, temporal position, reversibility, and evidence independence; faults originating in source data, agent reasoning, or computation are tracked along a separate source dimension rather than treated automatically as negative controls.In the geospatial domain, this taxonomy specialises along two domain axes. Along the spatial axis, faults comprise coordinate reference system (CRS) mismatches, topological errors, tolerance and boundary-attribution ambiguities, and spatial extent mismatches. Along the temporal axis, faults encompass currency (staleness) failures, observation-time versus valid-time confusions, coordinate-epoch errors, and version-timing substitutions—including provenance failures in which a returned dataset does not match the dataset, version, or spatial extent claimed in the output. The geospatial case audit (Section 4.1) is structured around this two-axis taxonomy.3.4 Three-tier evidence classificationEvery quantitative figure and governance status reported in this programme carries one of three evidence tiers, preserved faithfully throughout this paper:Tier 1 (independently verified): Recomputed or re-audited directly from primary artefacts (ledgers, trajectories, cryptographic hashes) by a party independent of the producer.Tier 2 (self-reported or single-source): Derived from producer-maintained records without independent recomputation.Tier 3 (planned): Events that have not yet occurred; plans, simulated runs, and design specifications are never reported as empirical findings.Acceptance is structurally separated from implementation: producers never self-certify frozen artefacts, and all frozen records are bound by cryptographic content hashes to enable drift detection upon re-audit. Whenever a reported number in Section 5 is Tier 2, its status is explicitly noted.4. Methods4.0 Common audit protocolAll domains adhere to a shared operational discipline. Task suites, fault instances, scoring rules, and numerical tolerances are frozen and hash-registered prior to the runs they govern. Wherever the interface allows, scoring is performed blind to arm identity against an oracle independent of the agent's self-report—specifically deterministic script recomputation, persistent fixture-state read-back, or independent re-derivation from authoritative source data. The oracle never resides within the agent runtime and receives no fault labels.Infrastructure failures (e.g., provider outages, transport timeouts, or unparseable helper outputs) are classified separately from model behaviour, logged individually, and—where pre-specified adjudication rules permit—removed from the substantive-error numerator without shrinking the intention-to-treat denominator. Every execution batch operates under a hard resource envelope (trajectory count, per-trajectory call cap, cumulative call ceiling, and expiry window); encountering any stopping boundary halts the batch immediately and is reported without retroactive renegotiation. For confirmatory-tier runs, provenance logging requires every usage and cost record to carry both its trajectory identifier and within-trajectory call index, ensuring deterministic joins across ledgers, usage logs, and scores so that unattributable records are explicitly counted rather than silently discarded.4.1 Geospatial domain: live-service audit (Study 1) and confirmatory apparatus (Study 2)The geospatial audit (Study 1) examined agent executions against live public geospatial web services rather than local sandboxes, cached replays, or static logs. Tool outputs were independently recomputed and adjudicated case by case under a four-way classification (correct, error, indeterminate, or specification ambiguity), with contested cases undergoing delegated first-pass classification subject to principal-investigator spot-checking and final approval. Study 1 serves strictly as an existence and mechanism audit: it demonstrates that target failure classes arise in live tool ecosystems and informs the fault classes operationalised in our injection suites. Because it lacks a population sampling frame, no incidence rate is estimated from it.The geospatial domain also hosts the programme's confirmatory apparatus (Study 2), whose governance status forms part of the audit record. A Slice 1 calibration design ($2\text{ operators} \times 4\text{ tasks} \times 3\text{ arms} \times 2\text{ conditions} = 48\text{ cases}$) is authorised under a capped resource envelope (at most 500 model calls and 1,250 credits). Adjudication is governed by a frozen tolerance ruleset specifying a 100 m point tolerance with per-point displacement $\ge 1{,}000\text{ m}$ for the reference-system operator, and a three-part conjunctive condition for the temporal operator. External ground-truth benchmarks for these calibration tasks (registration item O2) were assembled from four authoritative sources:USGS Geographic Names Information System (GNIS) domestic-names staged products;NCES Common Core of Data 2024–25 v1a Directory component (adjudication fields fixed to address and operational status);NOAA National Geodetic Survey (NGS) datasheets fixed as per-point text snapshots with retrieval timestamps; andthe Ministry of Civil Affairs national place-name database fixed as per-query snapshots of its 2025 annual edition.These benchmarks were registered as effective on 2026-11-19 following independent SHA-256 hash verification of all 35 snapshot artefacts (35/35 exact matches). The pre-run governance checklist for the calibration slice (F-03) has since been completed: the 48 calibration cases were generated as offline artefacts, accepted under independent F-03 review, and granted final principal-investigator approval on 2026-11-19. Study 2 has nevertheless not commenced: real model calls executed under this apparatus currently stand at zero.4.2 Browser-domain pilotThe browser pilot evaluated four models within a fixture-based web environment spanning 10 task families, each implemented as an isolated fixture equipped with a DOM/state-machine oracle and persistent-state read-back. Per model, the primary evaluation ledger contains 80 intention-to-treat design cells ($10\text{ families} \times 4\text{ conditions} \times 2\text{ arms}$). Experimental conditions comprised a clean baseline and three injected fault classes: F2 (silently corrupted values), F3 (label–target misalignment), and F4 (stale snapshot). The two main arms implemented the deployment line: stock (Playwright native API) and native (an agent-native CLI surface, moli-native v0.5 as frozen for the pilot). A standard browser MCP server served as a separate sensitivity arm (40 cells per model), reported independently and never pooled into the primary ledger.An additional batch (Native+V) augmented the native surface with an optional verification layer for one model (40 trajectories), evaluated against five predictions frozen prior to execution. Four models were tested: DeepSeek-V4.1-Flash (official API), Qwen3-8B (locally deployed, quantised, weights pinned by digest), DeepSeek-V4-Pro (official API), and GLM-5.3-Flash (official API). Scoring was conducted blind to arm identity. A subsequent adjudication pass (rulings J1–J8) reclassified eight infrastructure-failure trajectories out of the substantive-error numerator—four within the primary ledger—while preserving all intention-to-treat denominators at their full design sizes. All browser statistics in Section 5 derive exclusively from this frozen post-adjudication master ledger. In addition, a targeted discrimination experiment (Section 5.4) investigated one anomalous model–arm cell under three pre-registered mechanism hypotheses using a frozen run sheet.Two procedural disclosures accompany the browser pilot. First, the version-freeze threshold for the native surface was revised after an initial measurement was observed: under the original criterion ($\le 52$ total logged steps), the surface recorded 78 steps and failed to freeze; a documented change decision (CHG-BR-001) subsequently separated verification steps from task steps—without relaxing the numeric threshold of 52—under which non-verification task steps measured 44 and the surface froze. All references to the frozen native surface carry this disclosure. Second, one task family (FAM06) includes a pre-declared structurally incompletable cell on the native surface (a confirmation code embedded in a markup element unreadable by the native parser); by adjudication ruling, its four cells per model were retained in the primary ledger, and a common-capability-scope reading excluding them is noted alongside.4.3 Tabular-domain pilotThe tabular pilot evaluated two models: M1, DeepSeek-V4.1-Flash (provider model string `deepseek-flash`, official DeepSeek API), and M2, Qwen3-8B (Ollama model `qwen3:8b`, locally deployed); both were run at temperature 0 on 2026-11-14, with model identifiers verified against the pilot run configuration (`llm_backends.py`) and the provider model list on structured data-processing tasks (filtering, joining, aggregation, and reshaping) across two deployment-line arms: Arm A (adapted baseline) and Arm D (an agent-native surface incorporating a declaration gate requiring the agent, prior to delivery, to declare quantitative properties of its output—such as value bounds for named aggregates—which the gate verifies via system-side recomputation). Ground truth was computed by an independent deterministic script housed in a truth vault inaccessible to the agent. Conditions comprised a clean baseline and three tabular fault classes (T1–T3, corresponding to the framework taxonomy); T3 was structurally inapplicable to three task families lacking join or grouping keys, placing those 12 cells outside the evaluation matrix under a recorded change decision. In total, 148 trajectories were scored under the S/H/A taxonomy. Following scoring, an offline failure-chain audit examined every substantive-error consequence in the most informative model–arm cell to trace its underlying mechanism.4.4 Desktop domain: stage-0 feasibility probeThe desktop domain was scoped as a fourth testbed contrasting an operating-system accessibility-tree native surface with snapshot-scoped references (vercel-labs/agent-desktop) against the conventional screenshot-plus-pixel-coordinate paradigm. To date, only a side-effect-free stage-0 probe has been executed on a Windows laptop, exercising status verification and read-only snapshot read-back on a static window. Pass criteria, deployment constraints, and outcomes are summarised in Section 5.6. No task-bearing desktop evaluation has been run, and the frozen confirmatory protocol (Section 6) assigns the desktop domain to a separate wave outside the primary confirmatory ledger.5. ResultsAll figures reported in this section represent pilot or audit counts accompanied by their exact denominators and adjudication status; none support confirmatory causal inference. Where pre- and post-adjudication figures exist, the frozen post-adjudication ledger governs, and discrepancies are explicitly disclosed.5.1 Geospatial domain: case-level findings and unresolved governance stateThe Study 1 audit established the target phenomenon at case level against live public services: trajectories in which all execution-layer indicators returned nominal success, the agent completed its workflow without flagging any anomaly, and independent recomputation revealed a substantive spatial error—including CRS mismatches, layer version/timing discrepancies, and provenance substitutions. In additional cases, tool-chain faults were intercepted solely by external governance-layer review rather than by the agent's own checks. Because Study 1 is a case series without a sampling frame, no population incidence rate is estimated.The adjudication record itself highlights the difficulty of classifying real-world tool failures. A delegated first-pass review of 15 contested cases (the R-7 exercise) classified 6 as error, 7 as indeterminate, 2 as specification ambiguity, and 0 as correct. Governing decision records explicitly prohibit conflating boundary defects indiscriminately with "silent failures" and document two structural limitations binding this paper: (i) the geospatial engineering acceptance probe set (111 cases) and the per-case adjudication register represent distinct evaluation objects with no established mapping between them; and (ii) existing oracle checks rely on role separation (acceptor $\neq$ builder) and isolated-copy recomputation without blinding or an external independent oracle, and accordingly no claim of blinded independent-oracle verification is made.The geospatial governance state is itself a primary audit finding, as it rigorously bounds current claims. Formal ground truth remains unestablished for all 18 tasks in the geospatial evaluation suite (REAL18: 0/18, recording incomplete benchmark coverage rather than task failures). The Frozen Confirmatory Protocol (C1): Registered Future WorkNothing in this section reports empirical outcomes. The confirmatory protocol summarised below was formulated after three rounds of adversarial external review, revised via principal-investigator rulings on 2026-11-18, and signed frozen on the same date. It has not been executed, and this paper claims nothing from it beyond its registered design specification. A supplementary Open Science Framework (OSF) pre-registration embodying C1 has not yet been submitted [PENDING: OSF supplementary registration]; earlier programme registrations—the main registration (osf.io/3ushx) and browser supplementary registration (osf.io/eygbu), both embargoed until 2028-11-13 (DOIs pending)—remain unmodified, and the forthcoming registration will reference them uni-directionally as a standalone document.Experimental design. C1 operationalises the mechanism line via paired Arm B (optional verification) versus Arm C (mandatory verification) units executing over a shared backend with identical tasks, fault injections, models, and call budgets, differing solely in whether verification is optional or enforced on the execution path. The primary confirmatory ledger spans three domains (geospatial, browser, and tabular), with the desktop domain assigned to a separate wave by ruling. Trajectories are scored under the S/A/H taxonomy (Section 3.2), and the primary safety contrast is the paired difference in substantive-error consequence (H) incidence, $\text{C} - \text{B}$.Cluster randomisation and blinding. The unit of randomisation is the task-family cluster, defined by namespace and template lineage; tasks sharing template lineage or generative dependencies across domains, models, or conditions remain grouped within a single cluster and are never split to inflate cluster counts. Each paired unit comprises two exchangeable execution slots differing only in arm label. A single fair random bit per cluster assigns the slot-to-arm mapping across all pairs in that cluster, generated deterministically as the least significant bit of $\text{HMAC-SHA256}(\text{seed},\ \texttt{"C1-RAND-v1|"} \mathbin{\|} \text{cluster\_id})$. The 256-bit seed is drawn from an operating-system cryptographically secure pseudorandom number generator (CSPRNG) after the task roster freezes and prior to any confirmatory execution; only its SHA-256 commitment is logged in the run manifest. Seeds rotate per wave, re-rolling is prohibited, and infrastructure-failure re-runs preserve their original cluster bit and slot mapping. Paired slots remain strictly informationally isolated—no rejection traces, repair histories, or intermediate states cross between arms—and scorers remain blind to assignment tables until scoring concludes.Gate 1 (primary safety contrast). Inference is exact and conducted at the cluster level. Given per-cluster signed paired-difference statistics $g_f$ and test statistic $T = \sum_{f=1}^{F} g_f$, the reference distribution consists of all $2^F$ equiprobable sign-flip vectors induced by cluster randomisation. The exact one-sided $p$-value, $p = \Pr(T_{\text{flip}} \le T_{\text{obs}})$, is computed by exact enumeration via integer-scaled dynamic-programming convolution—never via Monte Carlo approximation. Confirmatory claims are strictly bounded to the sharp null hypothesis supported by the sign-flip distribution; no confirmatory claim is made regarding the weak null or an average risk difference absent a separately pre-approved calibration method. Delete-1-family jackknife influence diagnostics are reported descriptively and carry no decision vote.Gate 2 (composite availability gate). Gate 2 was revised on 2026-11-18 after an offline recount revealed that no individual sub-layer could attain the minimum denominator demanded by the draft gate: both the browser and tabular domains comprise exactly 10 independent families per layer, capping any per-layer denominator below the required threshold of 23. Restoring the hierarchy of the reviewed statistical basis document, Gate 2 is evaluated once on the pooled primary ledger as an intersection–union test of two mandatory criteria:Zero clean-subset regressions: On the clean paired subset, the count of B-correct trajectories blocked by the C gate—tallied under first-rejection-pair deduplication (a principal-investigator ruling explicitly registered because the statistical basis document's trajectory-level definition was silent on deduplication)—must equal zero ($k_{\text{clean}} = 0$).Bounded conditional kill rate: The one-sided 97.5% Clopper–Pearson upper confidence bound on the pooled conditional kill rate $\gamma_{\text{kill}}$ must be strictly less than $0.15$.To guard against intra-cluster correlation, a cluster-calibrated constraint is appended that can only tighten—never relax—the gate: the cluster-calibrated upper bound on $\gamma_{\text{kill}}$ (computed via delete-1-family jackknife standard error with a $t_{G-1}$ critical value as primary, and Webb six-point wild cluster bootstrap-$t$ as sensitivity) must also remain below $0.15$. All sub-layers (by domain, model, or condition) are demoted to descriptive reporting via point estimates and exact intervals, and any sub-layer with $n_{B=S} < 23$ is explicitly barred from binary non-inferiority verdicts. Earlier layered sample-size scenarios (74,080 trajectories across three domains; 84,320 across four) are archived solely as stress calculations; final confirmatory sample sizes will be re-derived under the pooled-ledger criterion and approved domain by domain, with no trajectory count or call budget authorised by the protocol signature itself.Gate sequencing and execution readiness. Gates 1 and 2 are tested in fixed sequence at one-sided $\alpha = 0.025$. All execution code is frozen by cryptographic hash prior to confirmatory execution; remediating clean-condition gate rejections is permitted exclusively during pre-confirmatory development and readiness checks, never once a confirmatory batch commences. Each domain requires independent acceptance readiness and separate envelope approval prior to launch. In the geospatial domain, the immediate pre-run prerequisites have been met in part: the 48 calibration cases have been generated as offline artefacts (generation was unlocked by the O2 benchmark registration in Section 4.1), the F-03 pre-run checklist has been completed under independent acceptance, and final principal-investigator approval of F-03 was granted on 2026-11-19. That approval covers the offline calibration artefacts only; execution of the calibration slice remains subject to separate run authorisation and envelope approval prior to launch, and no real model calls have been executed.7. DiscussionAlthough quantitative rates are not pooled across heterogeneous domains, the audit reveals a coherent descriptive pattern. Under fault conditions, substantive-error consequences are common—representing the modal outcome for every model in the browser pilot and the largest outcome category in the tabular pilot. Crucially, these errors are not primarily failures of surface fluency or effort. In the browser discrimination experiment, a frontier model exhausted its call budget against an interface whose accepted syntax diverged from its own manual; in the tabular failure-chain audit, a declaration gate passed 22 erroneous deliveries because its predicates missed the injected fault class and was circumvented in 2 additional cases when the agent edited its declarations instead of its underlying data; and in the Native+V batch, an optional verification layer was rarely invoked and, in the decisive trajectory, flagged an anomaly without altering the erroneous output. In every instance, failure concentrates at a seam—between documentation and driver, between verification predicate and fault space, or between diagnostic flag and execution commitment. Adapted tool ecosystems are structurally vulnerable precisely because adaptation creates these seams while leaving ownership divided between legacy human-facing software and newly added wrapper layers.These findings also discipline our programme's founding intuition. Nothing in the pilot data justifies a broad claim that agent-native packaging is inherently safer: browser arm differences were modest and inconsistent across models, the tabular native arm degraded error rates for one model while suppressing completions for the other, and adding optional verification to a native browser surface failed two of its five pre-registered predictions. Instead, the pilots motivate a sharper, testable hypothesis embodied in C1: the decisive design variable is not "nativeness" as an undifferentiated package label, but the wiring of verification—specifically whether checks are mandatory on the execution path, whether their predicates actually cover the target fault space, and whether checked invariants are anchored to system-side state that the agent cannot restate at will. On current pilot evidence, optional verification appears largely ineffective: agents under-utilise optional checks, while gates reliant on agent-supplied declarations invite compliance fabrication. Mandatory verification anchored to independent system invariants may substantially reduce substantive-error consequences—or it may simply trade errors for widespread incomplete trajectories, as M2's tabular Arm D profile warns. An observational audit cannot adjudicate between these possibilities; C1 is explicitly structured to do so, with Gate 2 designed to penalise any mandatory mechanism that suppresses valid completions regardless of how many errors it intercepts.A second implication concerns the state of agent evaluation methodology itself. Several of this paper's most consequential findings are negative facts about measurement readiness: a formal geospatial evaluation suite with ground truth established for 0 of 18 tasks, eight open freeze requirements, and a contested-case review in which 7 of 15 cases remained indeterminate even after delegated expert inspection. Benchmark studies in agent reliability routinely publish aggregate performance scores without auditing the adjudication substrate beneath them. We treat the unresolved governance state in Section 5.1 not as an external operational flaw, but as a central empirical finding: the gap between executing agents and knowing rigorously what occurred is itself a measurable property of an evaluation programme, and in live tool ecosystems it remains wide.Finally, the F2 ceiling effect carries a direct design lesson for future fault-injection studies. A fault class that produces 20/20 substantive-error consequences across all models and surfaces carries zero comparative signal; it operates as a manipulation check rather than an informative measurement instrument. Confirmatory agent-reliability studies should therefore treat fault-intensity calibration—establishing dose–response profiles per fault class—as a mandatory pre-confirmatory design step, a lesson the browser pilot surfaced by repeating a 20/20 failure row across all four models.8. LimitationsBecause this work comprises an observational audit and exploratory pilots, its limitations are structural rather than incidental:Absence of causal identification. No Arm B versus Arm C (optional versus mandatory verification) runs have been executed. All reported arm contrasts reflect whole-package deployment-line counts confounded by bundled architectural differences; accordingly, no statistical significance tests are reported in Section 5.Bounded pilot scope and sensitivity. The browser pilot covers four models, 10 task families, and one fixture suite; the tabular pilot covers two models and 10 families; and both incorporated fault intensities exhibiting ceiling effects in at least one class (browser F2). Because agent behaviour is highly sensitive to prompts, driver implementations, and model revisions—as illustrated by the DeepSeek-V4-Pro stock-arm syntax collapse—pilot counts should not be interpreted as invariant properties of the named models.Adjudication and oracle constraints. Post-hoc adjudication modified pilot numerators (eight browser trajectories reclassified under ruling J1; the frozen master ledger supersedes earlier summaries, shifting Qwen3-8B by two trajectories relative to pre-adjudication tallies). Geospatial oracle verification currently relies on role separation and isolated recomputation without blinding or an external oracle, while the tabular oracle shares structural assumptions with the task generator—a circularity risk mitigated but not eliminated by truth-vault isolation. Furthermore, two pilot parameters (the 12 T3-inapplicable tabular cells and the browser native surface freeze criterion CHG-BR-001) were revised via documented change decisions after initial measurements existed; both are disclosed where reported and illustrate the exact procedural flexibility that C1's pre-run freeze discipline is built to eliminate.Geospatial coverage limits. Study 1 is a non-probabilistic case series supporting existence and mechanism claims only. Because formal evaluation ground truth stands at 0/18, no geospatial reliability rate is currently estimable, and Study 2 has not commenced.Desktop feasibility scope. The desktop probe evaluated static windows for one tool version on one machine, establishing basic snapshot stability and an interactive-session deployment constraint without measuring task execution.Single-programme execution. All domains were engineered, executed, and adjudicated within a single research programme with AI assistance (see AI Disclosure). Independent external replication does not yet exist, and the independent acceptance roles specified in C1 remain unstaffed for most domains.Incomplete external registration timestamp. Although C1 is internally signed and frozen, its supplementary OSF pre-registration has not yet been submitted [PENDING: OSF supplementary registration]; until submission occurs, its public timestamp provenance falls short of the programme's earlier registrations.9. ConclusionAcross four domains, this observational audit demonstrates that LLM agents operating over adapted tool ecosystems incur substantive-error consequences at high rates under fault conditions. These failures cluster at adaptation seams—between documentation and driver syntax, between verification predicates and fault spaces, and between diagnostic flags and final commitments—and neither native packaging nor optional verification, as implemented in these pilots, reliably prevents them. Equally importantly, the audit exposes how thin the field's underlying measurement substrate remains: unestablished ground truth, open freeze gates, and contested cases that resist clean classification. Our response is procedural as well as empirical: a frozen, adversarially reviewed confirmatory protocol (C1) pairing optional against mandatory verification under family-cluster randomisation, exact sharp-null inference, and a composite availability gate that accounts jointly for missed errors and blocked valid work. Executing that confirmatory protocol—rather than expanding descriptive pilots—is the necessary next step.Data and Code AvailabilityPilot ledgers, scoring artefacts, and adjudication records for the browser and tabular domains are archived with hash-registered frozen summaries (the browser post-adjudication master ledger frozen on 2026-11-18; the tabular SUMMARY-COUNTS and verdicts files independently recounted at protocol signing).
